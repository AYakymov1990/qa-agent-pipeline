# Імпорт і класифікація чек-листа

Чек-лист приходить уже проаналізованим (окремий процес аналізу PBI) — тут його **не переписуємо**: тільки розбираємо і вирішуємо, хто виконує кожну перевірку.

## 1. Розбір — скриптом

```bash
.venv/bin/python scripts/checklist.py import --task <ID>
```

- Колонки — за заголовками (`pipeline.config.json` → `checklist.columns`): «ID», «Проверка», «Ожидаемый результат», «Примечание», «Прогон N».
- «Примечание» розбивається за « · » на позначки (`checklist.note_tokens`).
- Лист «Анализ PBI» — питання Q-xx, «Тип PBI», «Региональная версия», службові позначки.
- Повторний імпорт зберігає класифікацію рядків, текст яких не змінився; змінені — скидає з попередженням. `--reset` — почати з нуля.

Результат — `tasks/<ID>/checklist.json` (джерело правди) і `checklist.md` (для читання).

**Попередження імпорту** (немає пріоритету, немає «Данные», немає очікуваного результату, дубль ID, нерозпізнані позначки) покажи QA списком — це зворотний звʼязок автору чек-листа. Рядок без пріоритету в dev-режим не потрапляє.

## 2. Класифікація — перевір кожен рядок

Скрипт ставить чернетку за маркерами (`classification.manual`). Ти перевіряєш **кожен** рядок за `.claude/skills/qa-agent-spec/references/agent-suitability.md` і фіксуєш рішення:

```bash
.venv/bin/python scripts/checklist.py set --task <ID> CHK-014 CHK-015 exec=вручну "why=візуальний порядок полів" confirmed=1
```

| exec | Коли |
| --- | --- |
| **агент** | Результат однозначно перевіряється з тексту, значення, наявності елемента, ціни, помилки, URL, запиту в Network |
| **вручну** | Візуальний порядок і вигляд, ілюстрації, вигляд на планшеті / телефоні, автозаповнення браузера, буфер обміну, керовані затримки й помилки зовнішніх сервісів, порівняння зі старою збіркою, пошта / SMS, 3-D Secure |
| **API** | Перевірка без UI — через Network / Swagger |
| **автотести** | `[Регресс]` з повним покриттям — ставить `qa-autotests-coverage` |

Додатково:

- `needs_qa="<що>"` — передумова, яку може підготувати тільки людина (наприклад «QA заранее сопоставил тарифы»). Такий рядок не йде в dev-режим.
- Функціональну перевірку мобільної версії (видно, клікається, працює у вікні 390×844) агент робить; оцінку вигляду — ні.
- IP-залежні перевірки (`IP PT`, `IP FR`) — «агент», якщо в довіднику є рецепт зміни геолокації (перевірить `qa-test-data`); інакше — «вручну».
- Сумнів — «агент» з `why="сумнів: …"` без `confirmed`: у QA-режимі QA вирішить, у dev-режимі рядок іде як «агент» лише за P1/P2 і наявності даних.

## Режими

- **QA** (за замовчуванням): покажи зведення (`checklist.py status`), список «вручну» з причинами і сумнівні рядки; QA відповідає «так» або змінює окремі рядки — записуй з `confirmed=1`.
- **Dev** (`--auto --state <run>`): без запитань; усі виклики `checklist.py` — з `--state <run>` (спільний `tasks/<ID>/checklist.json` не змінюється). Рядки з `confirmed` не змінюй; решту класифікуй сам.

## Правила

- Формулювань чек-листа не змінюй, нових перевірок не додавай. Прогалина — у звіт «Помічено поза чек-листом».
- Рядок у `tasks/<ID>/pipeline.md`: кількість рядків, P1/P2/P3, агент / вручну / автотести, попередження.
