# Специфікація і кейси для агента

Мета — щоб агент виконав кожну відібрану перевірку **без жодного питання**: що відкрити, під ким, з якими даними, де і як побачити очікуваний результат.

## Вхід

- `tasks/<ID>/checklist.json` і `<run>/selection.json` — які CHK брати (тільки `take`).
- `tasks/<ID>/data.md`, `data_refs` рядків — дані; довідник і рецепти — `$CODEWIKI_PATH/kb/QA/`.
- `$CODEWIKI_PATH/kb/QA/PROJECT.md`, `glossary.md` — площадки, ролі, назви в UI.
- Документація (`$CODEWIKI_PATH`) і гілка розробника (`$AVTOPRO_PATH`, **тільки читання**) — щоб знайти дослівні тексти, ключі перекладів, ендпоінти для точок перевірки. Очікуваний результат з коду **не береться**: розбіжність код ↔ чек-лист — у «Помічено поза чек-листом», не в кейс.
- `.claude/skills/qa-agent-spec/references/agent-suitability.md`.

## QA-режим → `tasks/<ID>/spec/`

1. **Специфікація** `spec/spec.md` за `templates/spec.md`, глибина — за маршрутом: S — без специфікації (одразу кейси); M — сценарії і точки перевірки; L — повна (сценарії, обʼєкти і стани, точки перевірки, порядок, ризики). QA погоджує специфікацію L перед кейсами.
2. **Кейси** `spec/cases/TC-xxx.md` за `templates/TC.md` і `spec/cases/_index.md` за `templates/_index.md`:
    - один кейс — одна мета, один сценарій; CHK зі спільною передумовою і кроками — в один кейс, кожен CHK — окремий пункт очікуваного;
    - однакові кроки з різними даними, ролями чи площадками — один кейс з таблицею варіантів;
    - пріоритет кейсу — найвищий з його CHK; порядок у `_index.md` — P1 першими;
    - кроки — мовою намірів і **видимих назв** елементів (Playwright MCP працює зі знімком доступності), без CSS-селекторів;
    - очікуване — дослівно з чек-листа + як перевірити (текст, значення, стан, Network); допущення `Q-xx` — позначка «вердикт: потребує рішення QA, якщо факт ≠ допущенню»;
    - передумова з рецептом «Агенту можна: ні» — «готує QA», кейс не запускається, поки QA не підтвердив стан.
3. Статус нового кейсу — «чернетка»; «готовий» — після перегляду QA або розвідки.
4. Підсумок: скільки кейсів, які CHK покрито, що лишилось без кейсу і чому.

## Dev-режим → `<run>/cases/`

Без специфікації і без питань:

1. Для CHK, які вже покриті QA-кейсами `spec/cases/` зі статусом «готовий» / «стабільний», — **копіюй** ці кейси в `<run>/cases/` (позначка `from: spec`), не переписуй.
2. Для решти — кейси за тим самим шаблоном, статус «авто (dev)». Сумнів, як виконати крок, — рядок у «Перевірки без кейсу» з причиною, а не вигадка.
3. `<run>/cases/_index.md`, режим прогону — автоматичний.

## Правила

- Кожен відібраний CHK — рівно в одному кейсі або в «Перевірки без кейсу» з причиною.
- Не додавай перевірок поза чек-листом і не пом'якшуй очікуване.
- Ніяких паролів — тільки назви змінних `.env`; тільки тестові користувачі; тільки хости стенду.
- Жодне очікуване не сформульоване як «працює коректно».
