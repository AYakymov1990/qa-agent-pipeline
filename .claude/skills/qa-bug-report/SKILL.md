# Баг-репорт

Готує текст; баг в Azure DevOps заводить **QA сам** (pipeline нічого не пише в Azure DevOps).

## Вхід

- **Від агента**: FAIL з `<run>/report.md`, кейс TC, скріншоти `<run>/TC-xxx/`. FLAKY і «потребує рішення QA» — не оформлюй без підтвердження QA.
- **Від QA**: опис, скріншот, відео.
- Контекст: `tasks/<ID>/checklist.json` (CHK, «Источник»), `tasks/<ID>/data.md`, `$CODEWIKI_PATH/kb/QA/PROJECT.md` (severity, priority).

Бракує кроків або незрозуміло, що мало статися, — спитай QA коротко тільки про це.

## Що написати

`tasks/<ID>/bugs/BUG-xxx.md` за `templates/BUG.md` (без задачі — `tasks/_bugs/YYYY-MM-DD-<коротко>.md`).

1. **Заголовок** — `[<площадка>][<роль>] <Модуль>: <що відбувається> <за якої умови>`. Приклад: `[ES][Гість] Чекаут: при IP PT у País вибрано España`.
2. **Передумови** — «будь-який тестовий стенд <площадка> з гілкою `<гілка>`»; де відтворено — окремо (`es.seller1`, дата). Тип тестового користувача (без логінів), стан даних, прапорці, cookie. Посилання на сторінку — шляхом (`/cart/checkout/…`), однаковим на всіх стендах.
3. **Кроки** — нумеровані, мінімальні, з чистого стану, з конкретними даними; тексти UI — дослівно в лапках; без повних адрес з номером стенду.
4. **Фактичний** — дослівні тексти, числа, Network / Console (метод, ендпоінт, код). Без здогадок.
5. **Очікуваний** — дослівно з чек-листа: `CHK-xxx` і «Источник» рядка.
6. **Докази** — файли для вкладення. Місце зміни в гілці очевидне — «Можлива причина: `шлях:рядок` [ПРИПУЩЕННЯ]».
7. **Severity / priority** — пропозиція; вирішує QA. Пріоритет CHK (P1) — підказка, не правило.

## Видача

- У чаті — готовий блок для Azure DevOps: заголовок; нижче — передумови, кроки, фактичний, очікуваний (для «Repro Steps»); severity / priority; файли для вкладення.
- Статус: «чернетка» → «підтверджено QA» → «заведено» (QA вписує `ado_id`).

## Правила

- Один баг — одна проблема.
- Без емоційних оцінок, паролів, токенів, персональних даних.
