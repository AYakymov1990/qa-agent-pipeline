# Ревʼю базової структури

Для обговорення з другим тестувальником перед прогоном на реальній задачі. Нижче — рішення, прийняті за замовчуванням, і що варто перевірити.

## Прийняті за замовчуванням — підтвердити або змінити

| # | Рішення | Де змінити |
| --- | --- | --- |
| 1 | Мова артефактів pipeline — українська (як у попередньому pipeline); тексти чек-листа й UI — дослівно, як є (російська / іспанська) | `CLAUDE.md`, скіли |
| 2 | Прогони комітяться в `main` (`scripts/commit-run.sh`); `input/` — ні | `.gitignore`, `pipeline.config.json` → `runs` |
| 3 | Dev-режим пише тільки у свою папку прогону; спільні файли задачі — тільки QA-режим | `dev-check` |
| 4 | Контекст — у CodeWiki `kb/QA/`; pipeline пише тільки в `context-outbox/`, переносить людина | `docs/codewiki-qa-section.md` |
| 5 | Рядок без P1 / P2 / P3 у dev-режим не потрапляє (попередження імпорту) | `scripts/checklist.py`, `docs/checklist-format.md` |
| 6 | Dev-відбір: «агент», P1 → P2, без допущень, без передумов QA, без регресу, тільки з даними; ліміт S 8 / M 15 / L 20; P1 FAIL — P2 не запускається; бюджет 45 хв | `pipeline.config.json` → `selection.dev`, `routes`, `dev_check` |
| 7 | Чернетка класифікації — за маркерами в тексті (`classification.manual`); остаточно — скіл і QA | `pipeline.config.json` → `classification` |
| 8 | Статуси в «Прогон N»: PASS → «Успешно», FAIL → «Баг», BLOCKED / FLAKY → «Пропущено»; пояснення — примітка комірки | `pipeline.config.json` → `checklist.statuses` |
| 9 | Вердикт dev: ✅ — усі запущені P1/P2 PASS; ❌ — є FAIL; ⚠️ — BLOCKED серед P1 або прогін перервано | `dev-check` § 9 |

## Відкриті питання

1. **Вкладення через MCP.** Чи віддає Azure DevOps MCP вміст вкладення (xlsx)? Якщо ні — `ADO_PAT` + `scripts/ado_attachment.py` (кожному учаснику свій PAT) або чек-лист копією в коментарі.
2. **Геолокація за IP.** Багато перевірок залежать від IP (ES / PT / FR / UA). Чи є на стенді спосіб підмінити країну (заголовок, cookie, параметр)? Від цього залежить, чи це «агент» чи «вручну».
3. **Localhost для розробника.** Зараз хост — тільки `<site>.seller<N>.vus.us`. Чи потрібен запуск на локальній збірці (тоді — окремий шаблон хоста і правила)?
4. **Пісочниця і код.** `qa-agent-spec` і `qa-autotests-coverage` читають гілку AvtoPro. Чи дозволено це на Mac поза пісочницею, чи ці кроки виносимо в `sbx`?
5. **Довідник TD.** Хто його веде, як часто перевіряються записи (зараз «старше 30 днів — перевірить розвідка»)?
6. **Кількість одночасних dev-прогонів.** Кілька розробників на одному стенді і тестових акаунтах — чи потрібен розподіл акаунтів?
7. **Автотести.** Чи підходить схема `autotests/<ID>` у worktree з PR, який зливається разом із релізом задачі? Хто ревʼюїть?
8. **Формат чек-листа.** Чи погоджуємо `docs/checklist-format.md` з тими, хто пише чек-листи (P1/P2/P3 у кожному рядку, «Данные:», «Источник:»)?

## Що перевірити на реальній задачі

- Імпорт реального чек-листа без попереджень (крім очікуваних).
- Класифікація: скільки рядків «агент» QA перевів у «вручну» і навпаки → уточнити маркери.
- Dev-прогін від `scripts/dev-check.sh` до вердикту без жодного питання: час, вартість, чи вердикт збігся з оцінкою QA.
- QA-прогін: частка згоди QA з агентом (`calibration.md`).
- Колонка «Прогон N» відкривається в Excel без помилок, валідація і форматування збережені.
