# Як працює pipeline

## Межі

- **До pipeline** — аналіз PBI (ревʼю вимог, аналіз гілки, запити в документацію) і чек-лист без відкритих питань, вкладений у PBI. Це окремий процес і окремі скіли.
- **У pipeline** — агентна перевірка реалізації за цим чек-листом: QA-режим і dev-режим.
- **Після** — ручні перевірки QA, заведення багів, злиття оновлених автотестів з релізом.

## Кроки

| # | Крок | Скіл / скрипт | Вихід |
| --- | --- | --- | --- |
| 1 | Задача і чек-лист з Azure DevOps | `qa-ado-fetch` | `tasks/<ID>/input/` (кеш, не комітиться) |
| 2 | Розбір і класифікація | `qa-checklist-import`, `scripts/checklist.py import / set` | `checklist.json`, `checklist.md` |
| 3 | Маршрут S / M / L | `qa-test` § 2 | `pipeline.md` |
| 4 | Покриття регресу автотестами (QA) | `qa-autotests-coverage` | `autotests-coverage.md`, `exec=автотести` |
| 5 | Відбір під режим | `checklist.py select` | `<run>/selection.md` |
| 6 | Дані | `qa-test-data` | `data.md`, `data_status` |
| 7 | Специфікація і кейси | `qa-agent-spec` | QA: `spec/`; dev: `<run>/cases/` |
| 8 | Розвідка (QA) | `qa-agent-recon` | `spec/recon.md`, правки кейсів |
| 9 | Прогін | `qa-agent-run` | `report.md`, `results.json`, `checklist-<run>.xlsx`, `metrics.md`, `report.html` |
| 10 | Після прогону (QA) | `qa-bug-report`, `qa-autotests-update`, `qa-context-update` | `bugs/`, гілка `autotests/<ID>`, `context-outbox/` |
| 11 | Коміт | `scripts/commit-run.sh` | прогін видно команді |

## Класифікація перевірок

| exec | Хто | Приклади з чек-листів AvtoPro |
| --- | --- | --- |
| агент | Playwright MCP | вибране значення поля, текст помилки, наявність / відсутність елемента, ціна в сводці, створення замовлення на тестовому контурі |
| вручну | QA | візуальний порядок і вигляд, планшет / телефон (вигляд), ілюстрації, автозаповнення браузера, буфер обміну, керовані затримки й помилки зовнішніх сервісів, порівняння зі старою збіркою |
| API | агент або QA | перевірка без UI через Network / Swagger |
| автотести | AvtoProAutomation | `[Регресс]`, повністю покритий наявними тестами |

Чернетку ставить скрипт за маркерами (`pipeline.config.json` → `classification`), рішення по кожному рядку — скіл; у QA-режимі QA підтверджує (`confirmed`). Підтверджена класифікація зберігається між імпортами, поки текст рядка не змінився, і використовується dev-режимом.

## Відбір

| | QA | Dev |
| --- | --- | --- |
| exec | агент | агент |
| Пріоритет | P1, P2, P3 | P1, P2 (P3 — граничні — ні) |
| Допущення Q-xx | так, вердикт «потребує рішення QA» | ні |
| Передумова, яку готує QA | так, після підтвердження QA | ні |
| Регрес | якщо не покритий автотестами | ні |
| Дані | питання QA, якщо бракує | тільки `data_status=ok` |
| Ліміт | — | за маршрутом: S 8, M 15, L 20 |
| Порядок | P1 → P2 → P3 | P1 → P2; P1 FAIL — P2 не запускається |

## Маршрут S / M / L

За ризиком: гроші, статуси, інтеграції (Stripe, Recalvi, перевізники) → L. Маршрут визначає глибину QA-режиму (специфікація, розвідка, режим прогону) і ліміт dev-перевірки. Таблиця — `qa-test` § 2.

## Результати

- `results.json` — результат по кожному CHK: PASS / FAIL / BLOCKED / FLAKY.
- Копія чек-листа з результатами в першій вільній колонці «Прогон N»: PASS → «Успешно», FAIL → «Баг», BLOCKED / FLAKY → «Пропущено»; пояснення — у примітці комірки. Оригінал не змінюється; файл у PBI прикріплює людина.
- `report.html` — один файл: вердикт (dev), картки PASS / FAIL / BLOCKED, CHK, час і вартість, смуга покриття, деталі.

## Хто що пише (щоб QA і розробники не конфліктували в git)

| Файли | Пише |
| --- | --- |
| `tasks/<ID>/checklist.*`, `data.md`, `spec/`, `pipeline.md`, `bugs/`, `autotests-coverage.md` | QA-режим |
| `tasks/<ID>/runs/<дата>-dev-<хто>/` (у тому числі власна копія `checklist.json`) | Dev-режим — тільки свою папку |
| `tasks/<ID>/runs/<дата>-qa-<хто>/` | QA-режим |
| `tasks/<ID>/input/` | будь-хто; не комітиться |
| `context-outbox/` | QA, після підтвердження |

## Стан і відновлення

Стан — у файлах, не в памʼяті розмови. Повторний `/qa-test <ID>` читає `pipeline.md` і продовжує з першого незавершеного кроку; незавершений прогін (кейси «не запущено») — пропозиція продовжити.
